**Emulsion Library / Develop feature audit — 2026-09-28**

The highest-value work is faster interactive development, broader preset rendering, and stronger local editing. Emulsion already has a substantial catalog, RAW workflow and MCP surface. Adding more controls without improving the processing underneath would leave the main responsiveness and appearance problems unresolved.

This is a static code and workflow audit, not a new performance benchmark or photographic-quality certification. Proposed features below are not implemented by this document. Implementation should use Emulsion's own data model, GPUI controls, rendering kernels and independently written tests. No external application code, shaders, fitted tables, fixtures, assets or UI text are included.

The recommendations preserve existing capabilities: cached grid thumbnails, RAW/raster sidecars, RGB point curves, HSL, grading, snapshots, virtual copies, verified relinking, smart collections, stacks, local subject/sky models, sensor denoise, automatic perspective, metadata privacy, portable backups, WebDAV and MCP. These need extension and regression coverage, rather than replacement.

P0 means address in the next development cycle. P1 means follow once the required rendering/data foundations exist. P2 means a later expansion. Effort is relative scope, not a delivery-time promise. Camera-profile investigation can start during P0, but its implementation and validation are larger than an importer change.

**Why preview work comes first.** In [Library preview scheduling](../../../crates/emulsion-ui/src/batch/develop.rs), `library_raw_preview` calls `PhotoSource::develop_with` before `display_raster`. [PhotoSource](../../../crates/emulsion-io/src/photo_develop.rs) delegates RAW development to the full renderer. [The RAW pipeline](../../../crates/emulsion-io/src/raw/develop.rs) then demosaics again. Retaining a decoded mosaic prevents repeated file decoding, but does not eliminate this repeated processing. This is a code-path finding; latency still needs measurement on this machine.

A suitable first implementation caches an intermediate whose key includes all settings that affect that stage: source fingerprint, sensor denoise, camera profile, rendering version and any upstream calibration. Exposure/HSL edits should reuse that intermediate; changing sensor denoise must invalidate it. Preview-size processing and a later GPU path must retain CPU fallback and stale-result rejection. Existing [GPU infrastructure](../../../crates/emulsion-gpu/src/lib.rs) is useful, but a GPU UI does not automatically accelerate RAW development. Add GPU stages only after their CPU contract and profiling justify them.

Use compact display buffers and bounded caches to reduce memory. Preserve source precision and full-quality export. Converting camera RAW processing wholesale to 8-bit would not address redundant work and would lose editing headroom. Reduced-resolution previews should be identified as previews and refined at rest; full-resolution export must continue through the validated full-quality path.

**Preset fidelity requires actual rendering support.** The [parameter model](../../../crates/emulsion-core/src/raw.rs), [preset importer](../../../crates/emulsion-io/src/lightroom_presets.rs) and [detail stage](../../../crates/emulsion-io/src/raw/develop/detail.rs) show specific missing controls. Primary calibration must have its own camera-color operation; mapping it to the existing HSL mixer would change the meaning. Parametric curves should coexist with point curves, with documented processing order. Tests must cover combinations, not only one slider at a time. Before these algorithms change, add rendering-process versioning in [sidecar persistence](../../../crates/emulsion-io/src/raw_settings.rs).

Camera-profile support is feasible independently. The public [DNG specification](https://helpx.adobe.com/content/dam/help/en/camera-raw/digital-negative/jcr_content/root/content/flex/items/position/position-par/download_section_733958301/download-1/DNG_Spec_1_7_1_0.pdf) documents camera-profile matrices, tone curves and color tables. A bounded implementation can consume compatible user-supplied profiles without bundling proprietary assets. This does not imply support for every enhanced/adaptive profile. Profile identity and digest must persist in sidecars, history, virtual copies, export and backup manifests; missing or incompatible profiles must remain visible.

**Local editing should share the image-coordinate contract.** The current [LocalAdjustment model](../../../crates/emulsion-core/src/raw.rs) uses coordinates before crop and geometry. New masks and healing records should use the same documented convention. Existing [Photo Heal/Clone controls](../../../crates/emulsion-ui/src/editor/contextual_tools.rs) can inform reuse of Emulsion's own kernels, but applying destructive raster strokes to the RAW source layer is not a substitute for editable Develop records. Dynamic mask/spot collections will also require a bounded, versioned representation rather than indefinitely expanding the fixed eight-slot settings struct.

**Quality beyond adding controls.** Highlight recovery currently rolls off tones; the RAW source explicitly reports that saturated sensor-channel reconstruction is not performed. Investigate reconstruction on independently prepared clipped-highlight fixtures after the profile/float-stage work. Likewise, wider-gamut output needs a wider-gamut working path; changing the export profile alone cannot restore colors already clipped earlier. Native AI sensor denoise, HDR merge/output, panorama stitching and depth-aware blur are substantial separate projects and should not be presented as quick additions to this cycle.

**MCP is part of each feature's completion criteria.** Extend existing `develop_library`/`develop_raw` settings for tonal/detail/profile controls and expose their availability and profile resolution in inspection. Masks and spots need bounded create/update/delete/list operations with stable IDs. Culling, migration and proxy status belong in the existing Library tools. UI and MCP must use the same mutations, validation, undo/history, persistence and renderer. Tests should compare saved pixels after equivalent UI/MCP operations and verify clear errors for unavailable dependencies. New schemas alone do not constitute integration.

The recommended implementation sequence is:

1. Capture current render fixtures and latency/memory baselines; add rendering-process versioning. Implement numeric entry/reset and rate-and-advance as small workflow improvements.
2. Cache reusable RAW stages and introduce fit/region previews. Validate old source/preset output before adding optional GPU acceleration.
3. Implement the missing tonal/color families, then profile import and detailed sharpening/noise controls. Use the supplied Chic preset as one local regression case, alongside independently generated test inputs. Preserve honest compatibility reports.
4. Add direct crop/geometry interactions, composed masks and editable healing. Complete UI/MCP persistence and backup handling for every new asset type.
5. Expand catalog migration, read-only/proxy workflows and color-managed output according to measured demand.

Completion checks should include unchanged original bytes; backward-compatible old recipes; single-step undo for gestures; correct cache invalidation; bounded memory under rapid navigation; preview/export agreement within explicitly measured tolerances; and camera/profile/illuminant coverage. Preset import success must remain distinct from visual-equivalence claims.

Audit deliverable only: application behavior was not changed, and no new benchmark or runtime validation was run for this document.
